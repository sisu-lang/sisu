How fast is Sisu?

Eight small programs, each written with the same algorithm in Sisu, C, Rust, Go, Java and Python. The numbers show where Sisu stands today, not how fast it will be.

Where the gaps come from

Each gap was traced with callgrind and hyperfine, and by removing one cost at a time, by hand, from the program's LLVM IR.

binary_trees: the allocator and the counting

Sisu takes 0.79 times as long as C here, because it allocates with mimalloc and C calls glibc's malloc (ADR 0031). Callgrind counted 102 instructions in Sisu's allocator for each allocation and free, against 181 in glibc's, and 11.2 billion instructions for the whole program against C's 16.1 billion. What Sisu pays that C does not is mostly reference counting: a store when an object is made, and a load, subtract and store when it is released. ADR 0005 accepts that cost.

Java is fastest on this program. Its collector allocates by bumping a pointer and frees short-lived objects in bulk. It pays for that with five times the memory Sisu holds.

quicksort: the checks

Each element write checks the index against the bounds and the array's count against 1, and each addition checks for overflow. The checks are the whole gap to C. Removing the overflow checks by hand made no measurable difference.

A loop now makes the arrays it writes unique once, before it starts (ADR 0021). In a separate session on a busy machine, that took the fastest run from 690 ms to 640 ms, against C's 610 ms. The bounds checks remain: LLVM cannot prove the index is in range.

hello: the link step

Lexing, parsing and checking hello take 1.4 ms, timed with hyperfine on one pinned CPU after a warm-up. The whole sisu build -O2 build takes 27.6 ms, and the link through cc alone takes 21.9 ms of that. The bench script neither pins nor warms up its builds, so its 0.052 s reads higher. A faster edit-to-output loop starts with the link, not the compiler.

How it is measured

One script, scripts/bench.sh, builds each program in every language and times it. make bench runs it.

  • Each program uses the same algorithm in every language, written plainly, with no tuning for one language.
  • Each figure is the median of 9 runs. taskset pins every run to one CPU, so Go and the JVM see a single CPU, and the JVM picks its serial garbage collector.
  • Wall time is elapsed time. CPU time is user plus system time, so a garbage collector or JIT thread counts too. Both come from /usr/bin/time.
  • Every process runs whole, so startup counts: JVM startup and JIT warm-up for Java, interpreter startup for Python.
  • The inputs are constants in the source. No compiler folded a program to its answer: the run times grow with the input.
  • The checks differ. Sisu checks integer overflow and array bounds. Rust, Go and Java check bounds but not overflow. C checks neither.
  • A Sisu binary links its runtime, written in Rust, statically. That accounts for most of its size.

What these numbers cannot tell you

They come from one x86-64 machine, on small single-threaded programs. They show where Sisu stands, not how fast it will be.

Run them yourself

The script builds sisu in release mode, runs each program in every language whose toolchain is on PATH, and skips the rest. If mise installs Go and Java, put them on PATH with mise exec go java -- make bench. It prints the tables with the commit, date and machine.

Compile speed

How long Sisu, rustc, clang++ and Go take to compile the same program, in five steps. The compilers do different work, so a ratio shows where Sisu is, not who wins.

scripts/compile_speed.py repeats one unit, in each language, 10, 100 and 1000 times. Size 1000 is about 143k lines in Sisu, and 138k to 158k lines in the other languages. The unit has generic classes, an interface with an associated type, a generic function with a bound, an enum and string interpolation. Each copy has its number in a label string, so that rustc cannot merge the copies into one function at -O2. The main calls each copy twice. In Sisu and Rust, the run function of a copy is internal. LLVM gives the last call of an internal function a large inline bonus. With one call, LLVM inlines every copy into main at -O2. The time of the optimizer on one huge function grows much faster than the program: rustc -O2 took 14 minutes of CPU at size 100. Two calls remove the bonus. The C++ run function is external and never had it, and the inliner of Go has no such bonus.

The table shows size 1000, from commit 40ec062f on 2026-11-01. Other jobs ran on the machine during the run, so the times are noisy, most at size 10. The load averages for 1, 5 and 15 minutes were 13.2, 19.8 and 14.0 at the start of the run. They were 20.7, 17.8 and 13.7 at the end. The machine has 32 CPUs. Each time is the best of 5 runs. The sizes 10 and 100, the lines, the tokens and the instructions per token are in docs/benchmarks.md.

The scaling sweep

make scaling finds the programs for which a compiler stage costs more than a fixed amount for each unit of input. A shape is a kind of program that grows in one direction, such as more functions, deeper nesting or more match arms. scripts/scaling.py compiles each of 14 shapes at size 0 and at four sizes that double: n, 2n, 4n and 8n. It counts the instructions of each stage under callgrind: lex, parse, check, mono, mir and codegen. The count does not depend on the load of the machine. It needs valgrind, and a full run takes about 2 minutes on the machine above.

The script prints one table for each shape. It also writes table.md and counts.json to target/scaling/.

  • Growth is the count of a stage at one size, less its count at size 0. Size 0 takes away the fixed cost, such as the prelude.
  • Ratio is the growth at one size divided by the growth at half that size. A sweep has three: r1 (n to 2n), r2 (2n to 4n) and r3 (4n to 8n). A linear stage has ratios near 2.0, and a quadratic stage near 4.0.
  • A stage is judged when its growth at 8n is positive and at least 1% of the sum of the growth of the six stages at 8n. A stage that hardly grows with the shape is not judged. Its counts are noise.
  • A judged stage is superlinear when r3 > 2.3 and r2 ≥ 2.1, and when r3 ≥ r1 − 0.05 or r3 ≥ 3.0. The second test keeps a stage whose ratios fall a little toward 4.0.

The rule has two limits. It does not find a small quadratic part under a large linear part, such as 10000n + n². It also marks a linear stage that has one step in r2 and a rise in r3.

One shape and one stage that is superlinear for it is a case. The known list KNOWN in scripts/scaling.py has one row for each case that has an open issue: the shape, the stage and the issue number. The script exits with code 1 when a superlinear case has no row, when a row looks fixed, and when a check or a command fails. A row looks fixed when its stage is not judged, has no ratio, has r3 < 2.15, or has ratios that fall. The pull request that fixes a known case removes its row. At commit 889485b1, the sweep finds four superlinear cases, all in the check stage: array literal depth (#344), expression depth (#367), and type depth and method chain (#366). Generic call depth in check has the same cause as #366 and is just under the rule (r3 = 2.30). KNOWN has a row for each of the five. A nightly job runs the sweep and fails on a new superlinear case.

Regression tracking

The tables above compare Sisu with other languages. CodSpeed does something else: it compares Sisu with itself, change by change, so a slowdown shows on the pull request that causes it.

The CodSpeed workflow runs on every push to main. It also runs on a pull request that changes any of these paths:

  • crates/**, bench/** and selfhost/**
  • Cargo.toml, Cargo.lock, rust-toolchain.toml and .cargo/config.toml
  • the LLVM install: .github/actions/install-llvm/** and scripts/install-llvm.sh
  • the benchmark setup: codspeed.yml, codspeed-main.yml, scripts/codspeed-prep.sh and the workflow file

It runs in CodSpeed's simulation mode, which counts instructions rather than timing the run. It measures three things:

  • Seven of the programs above, all but hello, at reduced inputs, and eight programs that only CodSpeed runs, in bench/features/: strings, enum_match, shared_arrays, compare, tree_rewrite, interp, interfaces and show.
  • The lexer written in Sisu, selfhost/lexer.sisu: selfhost_lexer runs its -O2 build once on a fixed input of Sisu source, and build_selfhost_lexer is an -O2 build of it.
  • The compiler itself: an -O2 build of bench/hello, a sisu check and an -O2 build of bench/binary_trees, a sisu check of a generated 200-section input that uses most of the language, and an -O2 build of a 20-section one. Pushes to main also build the 200-section input, from codspeed-main.yml.

Before it measures, scripts/codspeed-prep.sh builds every benchmark and checks what each one prints. For the lexer, that is the tokens that sisu build --emit tokens prints for the same input. CodSpeed comments on a pull request when a result changes.

The check is informational: it never turns a pull request red. On a push to main, a failed step fails the run, so the benchmarks cannot stop running unnoticed. To compare a change before you push, make callgrind counts the instructions of sisu check on the large input, as CodSpeed does.
