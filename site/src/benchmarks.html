How fast is Sisu?

Where the gaps come from

Each gap was traced with callgrind and hyperfine, and by removing one cost at a time, by hand, from the program's LLVM IR.

binary_trees: the counting itself

Sisu takes 1.4 times as long as C here. The allocator costs the same in both programs. What remains is mostly reference counting: a store when an object is made, and a load, subtract and store when it is released. ADR 0005 accepts that cost.

Java is fastest on this program. Its collector allocates by bumping a pointer and frees short-lived objects in bulk. It pays for that with ten times the memory.

quicksort: the checks

Each element write checks the index against the bounds and the array's count against 1, and each addition checks for overflow. The checks are the whole gap to C. Removing the overflow checks by hand made no measurable difference.

A loop now makes the arrays it writes unique once, before it starts (ADR 0021). In a separate session on a busy machine, that took the fastest run from 690 ms to 640 ms, against C's 610 ms. The bounds checks remain: LLVM cannot prove the index is in range.

hello: the link step

Lexing, parsing and checking hello take 1.4 ms, timed with hyperfine on one pinned CPU after a warm-up. The whole sisuc -O2 build takes 27.6 ms, and the link through cc alone takes 21.9 ms of that. The bench script neither pins nor warms up its builds, so its 0.058 s reads higher. A faster edit-to-output loop starts with the link, not the compiler.

The programs

Each program lives in its own directory under bench/, with one file per language. All of them print the same output.

  • fibComputes fib(40) by naive recursionFunction calls and integer arithmetic.
  • sieveCounts the primes up to 50 000 000Array indexing in a tight loop.
  • binary_treesThe Benchmarks Game's binary-trees, depth 18Allocating and freeing many small objects.
  • helloPrints Hello, World!The time from source to output: build and startup.
  • quicksortSorts 10 000 000 pseudo-random integersElement writes, and in Sisu whether an array passed and returned is written in place.
  • nbodyThe Benchmarks Game's n-body, 5 000 000 stepsf64 arithmetic and sqrt, and field writes through shared objects.
  • mandelbrotCounts the points of a 4000 by 4000 grid that stay in the set for 50 iterationsf64 arithmetic in a tight loop.
  • fannkuch_reduxThe Benchmarks Game's fannkuch-redux, n = 10Reads and writes of small arrays, with short loops.

How it is measured

One script, scripts/bench.sh, builds each program in every language and times it. make bench runs it.

  • Each program uses the same algorithm in every language, written plainly, with no tuning for one language.
  • Each figure is the median of 5 runs. taskset pins every run to one CPU, so Go and the JVM see a single CPU, and the JVM picks its serial garbage collector.
  • Wall time is elapsed time. CPU time is user plus system time, so a garbage collector or JIT thread counts too. Both come from /usr/bin/time.
  • Every process runs whole, so startup counts: JVM startup and JIT warm-up for Java, interpreter startup for Python.
  • The inputs are constants in the source. No compiler folded a program to its answer: the run times grow with the input.
  • The checks differ. Sisu checks integer overflow and array bounds. Rust, Go and Java check bounds but not overflow. C checks neither.
  • A Sisu binary links its runtime, written in Rust, statically. That accounts for most of its size.

What these numbers cannot tell you

They come from one machine, on small single-threaded programs. Sisu runs on x86-64 Linux only, so there is nothing to compare on other systems. They show where Sisu stands, not how fast it will be.

Run them yourself

The script builds sisuc in release mode, runs each program in every language whose toolchain is on PATH, and skips the rest. It prints the tables with the commit, date and machine.

Regression tracking

The tables above compare Sisu with other languages. CodSpeed does something else: it compares Sisu with itself, change by change, so a slowdown shows on the pull request that causes it.

The CodSpeed workflow runs on every push to main. It also runs on a pull request that changes any of these paths:

  • crates/** and bench/**
  • Cargo.toml, Cargo.lock, rust-toolchain.toml and .cargo/config.toml
  • the LLVM install: .github/actions/install-llvm/** and scripts/install-llvm.sh
  • the benchmark setup: codspeed.yml, scripts/codspeed-prep.sh and the workflow file

It runs in CodSpeed's simulation mode, which counts instructions rather than timing the run. It measures two things:

  • Seven of the programs above, all but hello, at reduced inputs.
  • The compiler itself: an -O2 build of bench/hello, a --check and an -O2 build of bench/binary_trees, and the same two on a generated 200-section input that uses most of the language.

Before it measures, scripts/codspeed-prep.sh builds every benchmark and checks what each one prints. CodSpeed comments on a pull request when a result changes.

The check is informational: it never turns a pull request red. On a push to main, a failed step fails the run, so the benchmarks cannot stop running unnoticed. To compare a change before you push, make callgrind counts the instructions of sisuc --check on the large input, as CodSpeed does.
